## 一、跨域模式（比单条 bug 更该先处理）

### M1 · 「展开/平铺」把不该给的作用域数据带出去 —— 3 处独立复发
- `getMessages:650-661`（02）：无 `scope_type` 过滤，供应商定向消息对**所有门店角色含 chef** 可见。
- `getSupplierOrders`（04 H-5）：`...order` 展开，把**所有供应商**的 `supplier_confirmations` 下发给当前供应商。
- `getSupplierReceipts:104`（05）：平铺 `receipt_item`，泄露内部备注 `remark` 与处理结论 `resolution`。

三处都是同一写法习惯造成的，不是三个独立失误。**建议做一个「出参字段白名单」而非逐个修补。**

### M2 · 分批收货是系统性薄弱点 —— 一处数据结构错误，三处下游症状
根因：`receipt_item.order_qty_snapshot` 存**整单量**而非本批应到量（`createReceipt:278,497`）。
- 报表端（06）：汇总「下单数量」被成倍放大；带价报表详情 `.limit(1)` 永远只显示第 1 批。
- 供应商端（05）：分批收货**全部被误标「异常」**。

修一处数据结构，三处症状同时消失。这是本轮**投入产出比最高**的修复点。

### M3 · `settleReceipt` 是整条财务链的重灾区 —— 2 个域独立命中
- （02）`settleReceipt:916-923` 幂等用 `some()` 判 `_S` 后缀而非「全部供应商是否齐」→ 补充账单永久缺失（漏账）。
- （05 R1）**双付**：同一行先 `repriceReceipt` 再 `settleReceipt`，同一行被结算两次。
- （05 R2）`:942` 排除 `status='closed'`，异常用 `pay_received` 解决后再关闭即永久不结算，前端关闭按钮**无任何提示**。

## 二、Top 高危清单（按域）

### 01 身份
1. **停用→再启用复活旧会话**：`setUserStatus:499-504` 只清 `session_token_hash`/`session_expires_at`，没清 `sessions` 数组，而校验查的正是 `sessions`（`:109-112`）。`changePassword:305`、`resetPassword:461` 都清对了，唯独此处漏。
2. **`updateUser:393-440` 无自我操作保护、无「最后一个超管」保护**，而 `:446`/`:479`/`:484-493` 都有 → username 非 admin 的超管可自我降权锁死入口。前端 `user-manage.wxml:83-89` 无条件暴露超级管理员角色且无二次确认。
3. `getSessionUser` **复制 19 份**，`authService` 那份 legacy 分支语义与其余 18 份不同（不要求 token 在 `sessions` 内）→ 未来单点修改必分裂。

### 02 dataService
1. `settleReceipt` 幂等粒度错误（见 M3）。
2. `getMessages` 跨门店泄露（见 M1）。
3. `resolveAbnormal:796-826` 先置 `resolved` 再发 2 条消息且**无 try/catch** → 消息失败抛顶层错误，状态不可逆、重试被拒，「待补结算提醒」丢失直接导致账单缺漏。同文件 `auditOrder:588`、`remindAudit:1525` 有正确的降级实现，**唯独此处口径不一致**。

### 03 商品与价格
1. `importProducts` **无行数上限 + 逐条串行非事务写入** → 大文件超时后部分入库且无审计。
2. `getProducts` 无分页，且**搜索在 `limit(200)` 截断之后**进行。
3. `price_id = 'PRC_' + Date.now()` 无随机后缀 → 同毫秒改价撞号，前端按 key 定位可能点错行。
4. 完全无价格批量导入入口，价格只能逐条手录。

### 04 采购单
1. **H-1** 编辑草稿→提交：无条件更新 + 幂等复查只在新建分支 + 报表在事务外无幂等 → 并发双写同一草稿产生**两份不标 superseded 的报表**。
2. **H-4** `confirmSupplierOrder` 纯覆盖写 → 确认状态**可回退**、无审计、每次发货重复发消息。
3. **H-5** `getSupplierOrders` 越权（见 M1）。
4. 契约缺陷：`createdByName` 只进报表 CSV 不进库 → 复制草稿后报表经办人列为空。
5. `cancel_requested` 标记**全库无消费方**（申请取消闭环缺失）；`approval-detail` 无状态闸门；`getSupplierOrders` 按 `String(Date)` 字典序排序导致**跨月错乱**。

### 05 收货单
1. **R1 双付**（见 M3）。
2. **R2** 关闭后永久不结算且无提示。
3. **R3** 无幂等键，重试可绕过超收校验。

### 06 报表

## 四、正面结论（避免下一轮重复怀疑）

1. **权限架构方向正确**（01）：19 个云函数全部调用 `getSessionUser`，无绕过；权限全部靠云函数裁决；服务端按 `user.default_store_id` 强制作用域、不信任前端 `currentStore`。
2. **报表域未发现跨店/跨供应商越权**（06）；客户端伪造 `storeId` 无效；全链路先舍入到分再累加，**无一分钱尾差**。
3. **`createReceipt` 服务端权威化质量很高**（05）：商品/供应商/单位/下单量/价格/可付款资格全部库内裁决，事务内新鲜重算。
4. **已收数量不回写采购单**（05）：每次从 `receipt_item` 现场聚合，无陈旧聚合风险。
5. **凭证 `deleteFile` 修复确认到位**（05、08）：只删本单前缀内历史凭证。
6. **页面注册零差异**（07）：`app.json` 26 页 ↔ 磁盘 26 套四件套，无孤儿页；tabBar 8 图标路径全存在；19/19 `wx-server-sdk` 统一 `~2.6.3`；图标生成链 41 SVG / 88 组合无死代码。
